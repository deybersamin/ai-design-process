The route in one pass

Three loops keep problems close to where they started

A story becomes a scoped brief, then a working prototype on a preview URL. Visual QA and accessibility checks come first, then the PO approves. Design hands developers a prototype on placeholder data, and developers connect it to real data and logic. If QA finds a design problem it goes back to the prototype; a development problem goes back to integration. Figma and PrimeNG components and tokens feed both the prototype and the integration.

Phase 00: set up the foundations

Do this once, before phase 01. Design and dev together, in Claude Code. One-time work where judgment matters. Without it, nothing in the phases holds up.

Opus 5.5High effortClaude Code

    Make the right model the default, not a decision

    Set up in phase 00. Designers should not have to memorize a model chart. Defaults and step skills turn this playbook from guidelines people forget into the way the tools actually behave: the right model for each step, predictable token use, and the same process for everyone.

    1. Defaults for everyone

    Where

    Org-wide managed settings (set by admins) plus a shared settings file in the repo.

    What

    Default model: opusplan, so everyday work runs on Sonnet 5.5 and planning switches to Opus 5.5 on its own. Default effort: Medium. Only approved models available. Effort capped at Extra high, so nobody burns usage on Max by accident.

    Why it matters

    Most of the work gets the right setup without anyone touching a setting.

    2. One skill per step

    Each skill carries the instructions for its step and switches to the right model and effort while it runs. Then the session goes back to normal. Designers just type the name.

    3. Guardrails built in

    A person starts it, not Claude

    Skills that write outside the repo (opening PRs, filing bugs) can only be started by a designer. Claude drafts, you confirm.

    Reviewed like code

    Skills and settings live in the repo. Devs review changes in PRs, same as any other code.

    Stays current

    Skills point to model aliases (sonnet, opus), so they move to newer models automatically. Re-check the choices every quarter.

    4. Where it does not reach

    Regular Claude chat cannot switch models from a skill. For research, synthesis and the brief (phase 01), designers still pick the model themselves.

    What we do there

    A shared Claude Project with a skill for the brief template and synthesis instructions, plus a one-line reminder of the right model. The "Picking a model" guidance stays the reference.

    Start small

    Five skills for the most frequent and expensive steps. Add more only when the pilot shows a real need.

    How we will know it works

    Measure handoff, not AI usage.

    Baseline these before we start, then compare after the first few features:

    • Time from approved design to merged UI
    • Visual QA rounds per feature
    • Dev hours spent translating UI
    • Design issues found after handoff
    • How much of our UI code devs had to rewrite

    If devs end up rewriting most of our UI code, the process is not working, no matter how fast we prototype.

    Decisions we still need

    Phases 03 to 05 depend on these. Take them to the Design Lead and engineering.

    Storybook hosting

    Local only, or published (for example with Chromatic) so designers can use the Storybook MCP without running Storybook on their own machines.

    Prototype code

    Merged through a PR, or reference only? This playbook assumes PR. Reference-only keeps most of today's handoff friction.

    Claude Design

    Core step or optional? This playbook treats it as optional, to avoid a third source of design.

    Admin settings

    Which Claude tools and effort levels our org has enabled, and what Claude can write in Azure DevOps: read-only, or create work items and PRs. Plus who approves third-party skills like Impeccable, and the org-wide defaults: allowed models and the effort cap.
